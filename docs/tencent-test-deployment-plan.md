# Time_map V1.2 腾讯云测试部署前加固与部署方案

状态：待用户审核；本轮仅本地代码审查与方案编写。未连接腾讯云、未修改服务器/DNS/Caddy、未发送消息、未合并、未部署。

审查基线：Time-Management-Agent feature/v1.2 的 dfd4844，以及当前 Time_map feature/v1.2。正式实施前记录两个仓库精确提交并复核工作区。

## 1. 结论与范围

Notion读取、Gemini活动提取、真实地点备份匹配和两份独立飞书测试报告已验证；这不等于常驻云端服务完成。

服务器已有：新加坡轻量服务器、2核2GB、Ubuntu24.04、Docker、系统级Caddy。FreshRSS Compose位于 /opt/freshrss/compose.yaml，另有RSSHub、we-mp-rss和Redis。此前磁盘可用约25GB，内存余量有限；此前小时监控不能排除抓取瞬间峰值。这些是历史观测，实施时重新检查。

当前尚不具备直接公网部署条件。推荐顺序：本地加固实现和测试 → 服务器只读检查 → 备份与恢复证明 → 独立测试部署 → 手机试用 → 验收决定。原main、原手机站点和原自动日报保持当前状态，切换正式版本另行批准。

## 3. 测试拓扑与隔离

- 复用已确认域名 timemap.rychoz.com，但初期只承载独立测试API与预览页。
- 测试前端可放 https://timemap.rychoz.com/preview/，与现有正式Time_map站点不同来源；实际原站点URL先核对。这是测试入口，不让用户替换原主屏幕图标。
- API经Caddy转发至127.0.0.1上的独立端口，候选18120，实施时先确认未占用。只公开80/443，不公开数据库、API内部端口、Redis或管理端口。
- 测试数据库独立，先用合成数据；真备份只在用户批准后导入副本，手机原本地数据不覆盖。
- 初期设置“允许模型、允许发送”分别可控，默认都关闭；先测同步/结算，再逐项开放测试调用。
- 原GitHub Actions继续原流程；新服务器不另起一个同功能日报调度。测试飞书须使用明确测试标题，发送范围单独批准。

目录布局提案：

```text
/opt/timemap-test/
  releases/<发布标识>/       # 固定提交与镜像摘要，非main浮动更新
  config/                   # root管理的配置及秘密，权限受限
  data/                     # 测试SQLite及必要持久化发送状态
  backups/                  # 一致备份临时落盘，随后上传异机存储
  current                   # 当前发布指针，切换方法实施前验证
/srv/timemap-preview/<发布标识>/   # 静态测试前端，不含秘密
```

FreshRSS、RSSHub、现有Docker网络及Caddy其他站点保持独立；不执行全局清理或升级。

## 4. 资源与运行方式

2GB主机先采用API单进程、worker单并发，调度tick短时执行，不运行Ollama。开发初始压测预算可设API约192MiB、worker约256MiB、调度约64MiB，总新增上限约512MiB；这是待压测起点，不是容量保证。Caddy和RSS既有峰值也要算入。

先在本地受限容器验证启动和真实任务内存，再对照服务器空闲及RSS抓取峰值。若出现OOM、持续swap换入换出、任务超时或FreshRSS明显变慢，应停止测试服务、调整实现或升级资源，不通过关闭验证来强行上线。

容器重启策略、健康检查、CPU/内存上限及日志轮换写入Compose；数据通过显式持久化目录挂载。对外仅API；worker没有公网端口。启动时验证存储可写、配置齐全、迁移版本兼容。worker与调度必须使用相同的规则/应用版本。

## 5. 服务器操作顺序（供审核，尚未执行）

### 阶段A：只读盘点

获准后核对真实服务器标识、磁盘和资源、Docker及Compose版本、端口、Caddy实际配置路径和现有服务健康。记录结果时不打印env、完整docker inspect或秘密文件。

代表性只读命令：

```sh
sudo docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
sudo docker compose ls
sudo ss -lntp
df -h /
free -h
sudo docker stats --no-stream
systemctl is-active caddy
```

核对FreshRSS访问、RSS抓取基线与已使用端口。检查DNS前先确认该子域名无现有业务。Caddy路径以实际服务启动配置为准，不假定必为/etc/caddy/Caddyfile。

### 阶段B：先备份，再证明可恢复

按第六节完成FreshRSS与Caddy配置保护、服务器快照及新服务备份方案。先在独立目录/容器恢复并验证，拿不出可恢复证据则不修改Caddy或切换数据。

### 阶段C：仅本机部署新测试服务

创建独立目录、受限运行身份和数据权限；加载已审批固定发布包；秘密从服务器私有配置注入，不能复制云环境代理占位符。先禁用外发和自动任务。

以下命令仅在对应Compose、发布包及变量实际交付并审核后适用：

```sh
# RELEASE_DIR须为本次审批的真实发布目录，不使用main浮动检出。
sudo docker compose --project-name timemap-test --project-directory "$RELEASE_DIR" config --quiet
sudo docker compose --project-name timemap-test --project-directory "$RELEASE_DIR" up -d
```

不使用config输出完整配置，避免秘密展开。首次启动前先执行已审查migration，成功后本机请求health；未授权接口应401，带设备授权才允许读写。health不泄露配置，真实模式不再显示mock。测试PID/端口不能代替功能请求验收。

### 阶段D：接入HTTPS

添加timemap DNS A记录，确认80/443现有规则即可，不开放内部API端口。备份Caddy实际配置，新增独立站点，先validate再reload，不重启服务器或Docker。

站点结构示意，需结合实际配置审核，不能原样覆盖整个Caddy文件：

```caddy
# 仅为新增站点草案，不包含其他现有站点。
timemap.rychoz.com {
    @api path /v1/* /health
    handle @api {
        reverse_proxy 127.0.0.1:18120
    }
    handle_path /preview/* {
        root * /srv/timemap-preview/经批准的发布目录
        file_server
    }
    respond 404
}
```

部署包需补齐浏览器所需安全响应头、精确CORS、连接与body限制；具体Caddy指令先对实际版本校验。HTTPS通过后再检查FreshRSS原域名及RSS服务正常。不要把实际webhook、API密钥写入URL日志。

### 阶段E：手机与后台测试

新测试入口首次使用合成数据，确认独立存储后再考虑原JSON副本。按第七节逐项验证。逐步开放模型/飞书测试时记录范围和次数，防止费用与消息失控。

### 阶段F：提交验收结果

提供发布提交、镜像摘要、配置差异、测试结果、资源曲线、备份位置和恢复记录。未获最终批准不合并main、不替换原站点、不迁移正式数据、不改变原Actions调度。

## 6. 备份方案

### 6.1 第一次改服务器前

- 腾讯云控制台创建服务器快照，记录时间与快照ID，确认状态完成。快照可能需要额度/产生费用，执行前按用户批准范围处理。
- 备份Caddy实际配置、服务启动信息和现有站点配置；秘密单独保护，不把完整配置发到聊天或Git。
- 盘点FreshRSS数据持久化挂载及数据库类型。SQLite、MariaDB/MySQL采用各自一致备份/导出方式；不能直接复制正在写入的数据库文件或假设Docker镜像就是数据备份。
- FreshRSS若需要短暂停写以做一致备份，先说明影响并取得对应操作授权，不能自行停现有业务。
- 原手机导出JSON并确认已保存至另一位置。旧PWA不清站点数据、不卸载、不导入覆盖。

在线服务器快照只作为系统级补充，不代替应用一致性备份。

### 6.2 Time_map定期备份

- 每日通过SQLite backup接口生成一致副本，不直接cp正在写入的主库或遗漏WAL。
- 备份数据库、迁移版本、规则版本、镜像摘要、必要配置，以及发送outbox/回执状态。若发送仍使用文件队列，需统一备份窗口或迁入事务一致存储，不能恢复后重复发送。
- 临时文件写完并验证后原子标记可用，再上传服务器外的COS私有桶。
- SHA-256校验、SQLite quick_check及恢复后的schema/记录数/代表查询比对；定期再做integrity_check。
- 建议起步保留最近7份每日备份和4份周备份；升级前另留一份。桶私有、最小权限CAM、禁止匿名读取，采用服务端加密；保留与生命周期按费用审核。
- 秘密配置独立加密保管；备份凭据不让浏览器读取。备份失败产生提醒，但不在失败日志泄露路径中的秘密。
- 每周做一次自动恢复校验，每次数据库迁移前后做人工可复核恢复演练。

建议目标：普通灾难最多损失约24小时未备份云端变更（RPO），完成恢复约2小时（RTO）。这是待演练证明的目标，不是已实现承诺；手机未同步数据不包含在云端备份中。

## 8. 回退操作

### 情况A：新服务无法启动，尚未接入公网

停止timemap-test新容器，保留数据和日志，不动FreshRSS、原Caddy及DNS。修复后重新本机验证。禁止docker compose down -v或全局docker prune。

### 情况B：Caddy新增配置影响原站点

恢复本次变更前的Caddy配置副本，validate通过后reload；验证FreshRSS原站点恢复。然后只停止新服务。不要删除原证书数据或重装Caddy。

### 情况C：代码升级失败，数据库兼容

关闭新任务/发送入口，等待或记录在途任务；切换回已验证的旧镜像及静态包，使用原数据目录，验证API、报告和同步。确认schema兼容才允许直接回退代码。

### 情况D：数据库迁移不兼容或数据损坏

1. 停止新服务及worker，冻结当前数据库、发送队列、日志副本供分析。
2. 恢复升级前一致备份到新目录，用匹配旧schema的应用启动；不覆盖唯一现存副本。
3. 校验完整性、版本、记录、报告及发送状态；从备份后产生的有效变更经审查补回，不能直接把新schema库交给旧程序。
4. 首次恢复保持模型、飞书、调度关闭。核对已发送消息再恢复，防止把旧outbox重发。
5. 用户确认后再切换入口。恢复后客户端游标若高于云端必须明确冲突/重同步，不能自动清空手机。

### 情况E：服务器系统级故障

只有独立服务回退无法解决时，才考虑整机快照恢复或在新实例恢复。整机回滚会丢弃快照后的FreshRSS/RSS等数据，不是默认回退动作，必须说明影响并另行批准。

手机回退始终保留原PWA及原数据。测试站点数据不能自动覆盖正式站点；原站点地址保持，正式版本若需V2数据回退必须先兼容导出，不能仅换旧JS。

## 9. 后续需要用户提供的信息与授权

当前审核计划不需要密码或私钥。开始服务器盘点前需：

- 当前正式Time_map准确URL、FreshRSS域名（可安全提供或在授权会话读取），确认timemap子域名可用。
- 服务器接入方式：优先用户在控制台执行审核过的命令并提供脱敏输出，或另行授予受控访问；不要在聊天贴私钥/密码。
