### 2.1 Time_map

原生 HTML、CSS、JavaScript ES modules，无前端运行依赖。app.js 控制交互，storage.js 管理 localStorage，time.js 管理裁剪与汇总，sw.js 缓存应用外壳。现有部署为 GitHub Pages 静态站点。

本地键为 time-map-v1-data，schemaVersion=1，包含 places 与 segments。地点包含 id、name；片段包含 id、kind、start、end，地点段额外含 placeId、placeName。时间以毫秒时间戳保存，end=null 表示进行中。

必须保留：

- 常用地点增删改、到达离开、地点与路程切换、实时计时。
- 单一进行中片段、顺序及不重叠校验。
- 历史查看、跨天裁剪、编辑、删除。
- 编辑相连边界时同步调整相邻段；删除片段后保留空白。
- 删除常用地点不删除历史，改名更新历史显示及名称快照。
- 草稿校验后原子保存；失败不假装成功；损坏数据停止写入并可导出。
- 离线启动、离线计时、JSON 备份与恢复。

### 2.2 Time-Management-Agent

Python 通过 Notion API 读取源日程日期块、迁移至数据库，调用 Ollama 或 Gemini 提取活动；随后生成快照与汇总、更新项目统计、写回 Notion、更新 Life Calendar、发送飞书。

现有活动字段：event_name、duration_min、time_type、project_name、project_status、evidence。当前没有可靠起止时间与地点字段。分类规则写在提示词中。

保留原日报、有效与缓冲时间、项目完成统计、日周对比、Notion 写回、Life Calendar、GitHub Actions 自动运行和飞书发送。

generate_snapshot_and_summary() 含多项写入副作用；--no-feishu 仅关闭发送，不等于只读。手动分析必须使用独立入口。

兼容检查项：normalize_items() 保留新增字段；summary/Summary 属性名按实际配置统一；原 summary 解析格式保持；源日程“月.日”与 MIGRATION_YEAR 的跨年映射补齐。Life Calendar、原日报、地点利用率的分母分别保留，不混用。

## 三、已确认的产品规格

### 3.1 时间与查询

- 所有新结算及分析按 Asia/Shanghai，自然日为00:00至次日00:00。
- 原始时间戳不改，存储与传输使用 UTC 毫秒或带时区时间。
- 查询区间左闭右开 [start,end)，最长连续7×24小时；完整自然日查询最多7天。
- 支持昨天、前天、三天前、日期选择及自定义开始和结束时间。
- 进行中记录以本次固定 as_of 为临时终点，不写回结束时间。
- 旧版按设备当地日显示；升级后按北京时间显示。海外设备的日期归属变化需说明，不改变原始时间戳。

### 3.2 两种报告明确分开

Time_map 现有页面新增两种模式，仍从 iPhone 主屏幕图标进入；保留原前端站点地址与 PWA 身份。两种模式使用同一个起止时间选择器，均支持最多连续7天；仅选日期时默认北京时间自然日边界。

**地点时间流**：任意区间，例如08:00至次日08:00，提供地点时间流、到达离开、各地点停留、各段路程及总路程；不调用AI，不计算活动效率，离线可查看和复制。

**活动效率分析**：支持相同的任意区间，显示按天、按地点的停留时间、有效活动时间、明细及利用率；可独立发送飞书。完整自然日可使用明确日期、地点及持续时长的记录；部分自然日必须有可靠活动时间依据才计算归属。跨日分析先按北京时间分日，再按查询边界裁剪；区间利用率以有效总时长除以停留总时长，不直接平均每日百分比。

支持以下三类输入，固定格式与自然语言均为正式输入：

1. 开始与结束时间：“09:00—10:30｜图书馆｜阅读”或“早上九点到十点半，在北新桥图书馆阅读”。
2. 开始时间＋持续时长：“上午九点开始，阅读《某书》半小时”。由代码计算为09:00—09:30，AI只能摘取原文时间与时长，不得补造结束时间。
3. 仅持续时长：“在图书馆阅读半小时”。只在完整自然日且地点明确时归属汇总；部分日不按比例分摊。

开始时间＋时长可以确定性跨日：“晚上十一点半开始，写作一小时”对应23:30—次日00:30。显式起止跨午夜必须写明次日或可靠日期；“23:30—00:30”不自行猜测次日。“九点”缺少上午/下午时不生成精确区间，“09:00”作为24小时制接受。起止和独立时长矛盾时保留冲突证据，不选择其中一项悄悄覆盖。

无地点且时间可靠时按唯一同期地点日志匹配；明确地点尚未映射时列为待确认，不能当成无地点改配到其他地点。中文数字、半小时、一小时半、一刻/半点、日期边界纳入回归。来源证据必须可在原始块或父级上下文中核验，模型格式错误、编造证据或重复输出不直接入库。

旧记录只有持续时长时，完整自然日仍可汇总；部分日查询展示无法精确分配的活动与限制，不按比例摊分。若起止跨度与明确有效时长不一致，不假定整个跨度均有效。地点时间流不受活动时间信息缺失影响。

用户区分“查看已有报告”与“生成新报告/重新分析”：前者读取既有不可变结果，不读取Notion、不调用AI；后者重新读取日程并采用最新规则，创建独立报告。按钮明确说明其行为。

### 3.3 同步与失败处理

- 一个主要记录设备，保留设备授权与冲突检测，不开发多设备同时编辑体验。
- 到达、离开、编辑、删除、地点管理和备份恢复后记录变更并尝试同步。
- 先本地保存，后上传。断网不丢记录；启动、回到前台、网络恢复和立即同步触发补传。
- 显示最后成功同步时间、待上传数量、失败与冲突。
- 生成云端报告前先同步，失败默认暂停。用户可明确选择使用已有云端数据继续，报告必须注明未同步与数据版本。
- 本地区间查看和复制不受同步失败阻塞。

### 3.4 自动结算

- 默认北京时间01:30，结算前一个自然日，允许设置其他结算时间。
- 独立运行，不依赖手机后台。
- 迟到、编辑、删除触发受影响日期重算；不自动重发已发送日报，不因此修改项目累计或 Life Calendar。
- 日报发现结算未完成或过期时按需计算地点统计。
- 云端只能计算已收到的数据；同步完成不等于记录完整，空白与未关闭片段需提示。

### 3.5 原始活动与分类

- 原始 Notion 日程页面是活动唯一权威来源，迁移数据库不作为第二套独立活动来源。
- effective、buffer、ignored 三分类保留；规则由 Agent 统一配置，Time_map 不另设标准。
- 首版迁出现有提示词规则，再加入用户确认的类别与同义表达，不仅靠关键词判断。
- 同一次分析的原日报与地点章节使用同一批活动对象。
- 已经形成的报告永久保持原样；规则变化、Notion原文修改均不覆盖既有报告。
- 新生成的报告统一使用生成该次分析时选定的最新规则版本，包括报告中的旧日期活动。任务开始固定版本，执行期间不切换版本。
- 修改规则本身不触发历史重算。用户主动生成新报告时才重新读取旧活动并按最新规则分析。
- 新报告保存当次活动、分类、原文证据、来源标识、规则/提示词/模型版本及输入摘要，形成不可变快照。
- Notion原文纠错后，新分析更新当前活动投影或新增修订，并生成新报告；旧报告引用原快照，不受更新影响。源活动删除保留修订痕迹，新报告不继续计入已删除活动。
- 不要求还原旧项目没有保存的逐条旧分类；旧报告原样保留。需要重新分析旧日期时直接读取原文、按最新规则生成新结果，明确为新的分析。
- 例：旧规则下运动不算有效，后来加入有效范围。旧报告不变；主动生成含旧运动的新报告时，运动按最新规则算有效。

### 3.6 Notion读取时机

Notion客户端编辑由Notion自身同步到其云端；本系统不实时订阅每次日程编辑，也不持续复制全文。自动日报执行、手动生成或重新分析时，读取所选日期最新的原始日程；普通查看已有报告不重拉数据。一次任务保存其实际读取版本与时刻，不承诺跨多次请求的绝对原子快照；发现读取期间变动则重试或标注限制。

## 四、地点匹配与效率计算

新增活动字段：源页面与块 ID、内容摘要、所属日期、地点原文及地点 ID、可空起止时间、时间精度类型、地点与时间证据、分类版本、异常标记。完整活动保留源ID与跨日归属，跨日裁剪不能重复计数。

匹配原则：

1. 日期、地点和持续时间明确即可进行完整自然日汇总，不要求用户逐条记录开始与停止时间。
2. 无地点但有可靠起止时间，可与唯一且一致的地点片段匹配，标注“依据时间匹配”。
3. 无地点、无可靠时间的活动归入地点未知，不由 AI 猜测。
4. 有时间和明确地点但与地点日志矛盾时，提示异常，不以任一来源静默覆盖。
5. 别名映射需明确确认，AI 可提出候选，不自动合并地点。
6. 同一地点多次停留按原地点 ID 汇总。

地点有效时间为归属于该地点的有效活动时长；利用率为该时长除以地点停留时长。分母为零不可计算。

重复、活动重叠、日界线不明、有效时间超过停留时间均列异常，不简单截断或抹平。同一时长不能分配至多个地点。无法证实时不生成精确比例，可显示已确认有效时间和限制；已确认比例若仅为下限必须明确标注。

“非有效时间”展示为“未确认为有效的停留时间”，不等于浪费。未知地点、未知时间及冲突分别呈现。路程单列，不进入地点停留分母。

## 五、系统架构

采用腾讯云 FastAPI＋SQLite。Time_map 保持静态前端，通过 HTTPS API 访问后端，不直接访问数据库，不在 GitHub 保存个人地点日志。

数据流：

1. 手机操作 → 本地原子保存和同步队列 → Caddy → FastAPI → SQLite。
2. 定时器 → 地点原始记录 → 自然日结算及完整性状态。
3. 原 Actions 日报 → 原始 Notion 日程 → 当次不可变分类快照 → 地点匹配 → 原日报新增地点章节。
4. 手动报告 → 同步确认 → 独立任务 → 地点报告或区间活动效率报告 → 独立飞书消息。
5. 云端缺记录 → 可读取 Notion 备用日志补缺 → 保留来源和去重信息。

腾讯云部署同一 Agent 仓库的分析模块，由一个独立后台任务执行器串行执行手动任务。现有 Actions 自动日报保留，访问版本化地点与分类接口；不复制维护两套分类代码。

后台任务持久化到 SQLite，具备领取、租约、超时和重试，不能只依赖 Web 进程内临时任务。SQLite 单机部署，不横向扩展多个写服务；事务保持短小，AI/网络调用不占用长事务。

## 六、本地存储与同步协议

### 6.1 兼容迁移

保留原 V1 存储，写入独立 V2 封装，迁移成功验证后启用。原 ID、毫秒精度、地点快照保持；失败继续使用 V1，不覆盖损坏数据。

V2 将业务记录、待同步变更及必要版本元数据一次持久化，避免“记录已保存、队列未保存”。保留 V1 导入，新完整备份不包含认证秘密。上线前导出原数据，回退通过兼容导出恢复新记录，不只切换网页版本。

先复用 localStorage，验证现有最大数据量和空间失败；必要时才引入 IndexedDB，不无条件重构。旧标签页继续写 V1 的问题需通过版本提示与迁移协调测试处理。

### 6.2 上传与冲突

- 请求含 batch_id、device_id、base_revision、operations。
- 关联编辑、离开或到达涉及多个片段，作为原子批次提交。
- 服务端校验类型、时间、排序、重叠和单一进行中片段后事务提交。
- 重复批次返回原结果；超时保留本地队列，退避重试。
- 单调修订号与变更游标支持分页拉取；落盘后再推进游标。
- 删除保留墓碑；快捷地点删除与历史片段删除分开。
- 冲突返回409及差异，不用手机墙上时间强制覆盖。
- 备份恢复为显式差异处理，不将缺失项自动当成云端删除。
- 长期离线或游标过期时使用完整校验/重同步，不静默丢变更。

数据集内实体 ID 唯一，批次 ID 唯一；索引覆盖区间、游标、结算日期及待处理任务。具体 migration 在开发阶段审查后实施。

| API | 用途 |
| --- | --- |
| POST /v1/sync/batches | 提交幂等原子变更 |
| GET /v1/sync/changes | 分页拉取变化 |
| GET /v1/segments | 返回区间片段、来源修订号 |
| GET /v1/settlements/{date} | 日结算及完整性 |

每次用户主动重新分析创建新任务版本；网络重试沿用原幂等键。任务状态 queued、running、succeeded、partial、failed，发送状态单独管理。

所有报告记录地点修订号、Notion 来源摘要与读取时刻、规则版本、生成时刻。读取中发现来源变动则重试或标注不一致。不得把旧缓存冒充最新。

## 八、报告与副作用隔离

自动综合日报：原活动、有效/缓冲时间、项目、日周对比保留；末尾追加地点停留、有效活动、路程、未知与异常，以及有证据支持的建议。地点模块失败时保留原日报，并说明地点章节失败，不能显示零数据代替失败。

手动报告允许更新当前活动投影和修订，并写独立任务、结果、发送状态；不得调用项目累计更新、Notion 日报写回或 Life Calendar 更新，不覆盖既有报告。地点结算及分类快照是分析基础设施，不属于长期累计时间更新。

飞书检查 HTTP 和业务返回码；长报告分段，保留分段 ID。外部 webhook 超时可能已送达而回执丢失，标记不确定并控制重发，不承诺绝对只发送一次。

## 九、Notion 备用补缺

用户创建普通页面“Time_map 地点日志备用”，授权现有 Notion 集成。无需数据库。该页与原始活动日程分开。

未来复制按钮生成日期、时区、导出时间、地点/路程起止与时长，以及记录 ID、版本和可校验的结构化信息；用户粘贴完整区块，不需手写技术字段。

正常同步无需操作。备用只补云端缺少记录，同 ID 去重；同 ID 不同内容提示冲突。备份文本不自动覆盖云端，不用于复杂删除修复。若备用与云端版本无法证明一致，报告注明限制，不声称最新完整。

## 十、服务器、HTTPS、安全与备份

### 10.1 已知条件

腾讯云新加坡轻量服务器，2核2GB，Ubuntu Server 24.04 LTS，Docker 环境。FreshRSS 为 Compose 项目 freshrss，配置 /opt/freshrss/compose.yaml。另运行 RSSHub、we-mp-rss、Redis。Caddy 系统服务运行，监听80/443；Nginx 系统服务未运行。

磁盘可用约25GB；近7天小时粒度 CPU 平均约3.26%、最大18.05%，内存监控约784至822MB；此前 available 约797MiB。小时统计可能平滑短时峰值，不能保证瞬时余量。基础 HTTPS 请求已收到 Notion、Gemini、飞书响应，真实授权尚未验证。

当前没有腾讯云快照，也没有用户自行配置的其他备份。

### 10.2 部署方案（待另行批准执行）

- 后端域名 timemap.rychoz.com，DNS A 记录指向服务器。
- 独立 Compose 项目与数据目录，不改动 FreshRSS 项目。
- FastAPI 单 Web 进程，分析任务串行，使用远程模型。
- 内部端口部署前查占用，仅绑定回环；复用 Caddy 新增独立 HTTPS 站点，先校验再重载。
- 前端继续原静态站点，不默认迁移现有站点地址，避免浏览器本地存储因换源无法直接读取。
- HTTPS、设备配对、可撤销设备凭据、最小权限服务凭据、限流、请求大小和时间范围校验。
- 密钥仅存服务端保护配置/Actions Secrets，不在前端、备份、Git 或聊天中公开。
- 精确 CORS；若用 Cookie 则有 CSRF 防护；API 私有数据不进 Service Worker 缓存。
- 观察抓取峰值，限制任务并发；必要时错峰。不上本地大模型。

### 10.3 真实集成验证

用户另行批准测试后，读取指定 Notion 测试日，发起最小 Gemini 请求，向测试飞书群发送明确测试消息。分别检查权限、模型额度、业务返回，不将根路径302/404当成真实API成功。

### 10.4 备份与恢复

每日使用 SQLite 支持的一致性备份方式生成副本，上传服务器外私有存储，例如腾讯云 COS；数据库文件不公开。保存必要配置，密钥独立保护。

部署前创建服务器快照，作为系统回退补充。建立备份失败提示、保留期限与恢复演练。恢复到独立目录检查记录数量、版本及代表性查询。

每日备份的最坏云端数据损失窗口约一天；本地记录及手动 JSON 备份为补充。具体保留期限、COS 权限及恢复目标在部署审查确定，未实施前不宣称已有可靠备份。

## 十三、主要风险与完成标准

- 历史报告：结果及输入快照不可变，当前活动修订不能改变旧报告；新报告明确记录最新规则，不声称还原旧AI决定。
- Notion层级重复和同日期多页：保留来源ID，歧义报错，不默认选第一条生成精确新报告。
- 原summary解析：主指标格式保留，新增章节不污染旧正则。
- 数据完整性：缺记录、未同步、未关闭、冲突分别提示，不以零代替失败。
- 同步和恢复：墓碑、修订号与显式差异，防止复活删除项或误清空云端。
- 服务器资源：小时监控不足以排除尖峰，灰度验证单任务资源与RSS抓取共存。
- PWA与域名：后端子域名不改变前端存储源；升级有兼容与回退验证。
- 外部消息：发送不确定与分析失败分开，避免重试造成重复消息。

完成标准：V1功能及原始数据保留；同步、结算、备份恢复可靠；区间地点时间流准确；区间效率可追溯；旧报告不因规则或数据变化而改变，新报告使用最新规则；手动报告不改变长期统计；用户审查通过后才能合并部署。

## 十四、配置前提与授权

功能范围无待决边界。开发前只需用户明确批准，不要求先提供全部在线凭据。可用脱敏夹具与模拟API开发、验证纯逻辑和同步协议；未提供凭据的在线步骤保持未验证，不声称通过。

云开发环境中的LLM_PROVIDER=gemini、APP_TIMEZONE=Asia/Shanghai可保留。NOTION_SOURCE_PAGE_ID指向权威原始日程；NOTION_DATABASE_ID及PROJECT_DATABASE_ID用于保留的原日报和项目流程。NOTION_TOKEN、GEMINI_API_KEY通过安全设置填写，验证页面已授权给对应集成。FEISHU_WEBHOOK_URL、备用页面ID、原属性名、模型配置等在真实联调前按需配置，不把秘密写进文档或代码。

云开发环境、GitHub Actions、腾讯云服务器是不同执行位置。一个位置填入凭据不等于其他位置已配置；按各自最小权限安全配置。完成环境设置不会启动项目开发、发送报告或部署。

真实Notion读取、Gemini请求、飞书发送需具备可用凭据和相应测试授权。Gemini请求可能产生费用；飞书使用测试群。服务器操作、DNS、Caddy、COS与正式部署按批准范围实施，不要求用户在聊天提供密码、私钥或Token。

部署前确定备份保留期限、存储桶、实际内部端口及测试群；这些为实施配置，不阻塞规格定稿。若真实接口或原数据揭示新歧义，暂停相关步骤说明证据，其余授权工作可继续。

## 十五、最终验收补充

- iPhone主屏幕原入口仍可打开，原数据及计时保留。
- 任意≤7天区间，两种模式均可使用；地点模式不调用AI，效率模式正确按活动起止与地点求交。
- 旧时长-only活动在完整日可用，在部分日不伪造精确归属。
- 普通打开旧报告不重算；重新分析读取最新Notion并用最新规则创建新报告。
- 修改活动时长、性质或删除活动后，当前分析数据及新报告更新，旧报告字节内容和原输入快照不变。
- 只改规则不自动重算；含旧活动的新报告采用最新规则，旧报告不变。
- 手动分析不更新项目累计、Notion日报字段或Life Calendar；更新仅限当前活动修订、独立分析及发送状态等分析基础设施。
- 不将报告快照与当前活动投影混用，验证修订、删除和规则变化均不会间接改变旧报告显示。
- 两个项目docs/time_map_spec.md在开发获批后保存本规格；实现与规格变化同步记录。


## 十六、接口适配补充（2026-10-28）

Notion适配器仅GET原始日程块，分页读取层级及来源ID，按年份映射源页面，跨年标题歧义及重复日期报错。区间包含前一日以覆盖跨午夜活动，不能重复计入仅时长活动。

模型适配器支持Gemini结构化JSON和Ollama schema；统一规则随请求发送，代码独立校验原文证据并计算时间。飞书适配器检查HTTP与业务码，发送超时标为不确定，不盲重试。默认真实传输关闭，构造或导入适配器不产生请求。本阶段只使用模拟HTTP和模型响应，不宣称真实模型语义准确率已验证。
