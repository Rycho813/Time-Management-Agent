# 仅记录地点、活动名称和持续时长的匹配

用户不需要补活动开始/结束时间。完整自然日的活动按原文地点与当天手机日志归属，不从时长推算时刻。原有明确起止时间记录继续走时间交集计算。对应算法版本为place-duration-v1，作为place_match_version写入新报告；分类规则及历史报告保持原样。

## 归属依据

1. 原文明确“在/位于某地”优先，避免把后面计划前往的目的地当作当前地点。
2. “逛/到访/参观甲店/乙店”保留整个组合；模型即使只提取了其中一家，代码也不会把总时长全算给这一家。
3. 其他原文明示地点由模型摘取原词，代码使用手机当前地点名、历史记录中的地点名和可选别名TIMEMAP_PLACE_ALIASES匹配。不是靠活动名称猜地点。
4. 活动本身没有地点时，可继承明确地点父标题。working、reading、起床时间等一般标题本身不产生地点，“吃饭/起床”不自动归到家。
5. 同名地点存在多个ID时，结合该活动日期实际到访记录缩小候选；仍不唯一就保留待确认，不根据容量“挑一个看起来合适的”。配置别名与现有地点名冲突也不会静默覆盖。

一天内多次到同一地点，按该地点ID合计停留，再汇总活动；不把活动编排进某次停留，也不生成matched_start/matched_end。活动保留reported_place_duration归属依据；真实起止时间匹配保留time_intersection依据。上午、晚上等描述不被转成模型猜测的时刻。

## 总量与不确定性

- 有效、缓冲、未计入活动都占用地点容量。累计活动时长超过停留时提示冲突、利用率置为无法确定，不截断、缩放或更改活动分类来凑数。
- 多地点合计时长没有各店明细时，组合总量只保留一次，不均分、不按停留比例分配，也不在每家各重复计一次。日报全局活动时长仍只计一次。
- 组合若含有效活动，涉及的可识别地点利用率保留不确定；不会把尚未归属当成这些地点有效活动为零。其他地点在不存在相关歧义时仍可计算。
- 地点当天没有手机停留记录、别名未匹配、地点缺失、地点歧义均提示原因。未归属的有效活动可能影响利用率确定性，不能仅凭部分已匹配活动声称完整利用率。
- 仅时长活动只归原始日程日期；部分日/任意小时区间不能按比例摊出活动时长。跨午夜但无起止时间的记录也不猜测跨日分配；明确起止的旧记录继续按北京时间分日。
- “逛书店”等活动仍按现有分类规则和原文语义分类，不能只因上级标题为reading就自动视为有效。真实模型语义尚待获批联调。

## 呈现

完整日报的地点章节增加活动明细，例如示例图书馆下显示“开发示例项目：25分钟（有效）”。“已确认有效”改称“已归属有效”，避免暗示已还原精确活动区间。组合与无法归属的活动在待确认区域展示。独立报告和网页历史视图使用同样的数据；地点时间轴仍只显示手机记录的地点/路程时间，不生成活动时间轴。

代码测试使用脱敏合成文本；没有将用户截图原文、手机JSON、真实地点清单或凭据提交Git。离线检查用户已上传地点文件只用于确认两个明确地点的命名匹配，不修改原文件、不访问服务器或模型。

## 部署与阶段

这次迭代属于第1/4步（匹配逻辑及离线验收），随后依次为2/4真实只读分析、3/4完整写回和飞书验收、4/4单一调度。原运行环境已完成的验证仍有效，但旧d2fe00e日报镜像不包含本次逻辑，不能拿它冒充新版本做验收。

新增deploy/prepare_daily_context.py与deploy/Dockerfile.daily，解决API的.dockerignore排除旧日报脚本的问题，并显式打包新backend/place_matching.py。准备工具仅导出固定Git对象的已允许源码、活动规则和Dockerfile，不复制.env/runtime.env、手机数据、.git或仓库.dockerignore，不构建或启动服务。Dockerfile要求context-manifest.json，直接用旧API源码目录构建会失败，避免再得到缺脚本却构建成功的镜像。

后续可用已审核API镜像作为依赖基础，但必须记录并验证实际基础镜像ID、显式复制新提交的backend代码与旧日报入口。分类规则也来自同一新提交。基础依赖版本与应用源码版本分开记录；不修改旧API镜像、image.json或检出。新日报可以独立测试；若以后开启网页活动效率API，也须另行升级对应后端，不假定旧API自动拥有新匹配逻辑。

本轮不部署、不启用模型/发送/定时器、不改服务器数据库。所有真实调用和写回仍须明确授权。
